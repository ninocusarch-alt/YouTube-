# 项目交接文档设计规范

## 目标

为 Real-time AI Video Companion 建立一份可长期维护的阶段性交接文档，同时满足两类用途：

1. 支持项目复盘、简历复查和面试准备，能够区分产品判断、个人贡献、客观证据与尚未验证的假设。
2. 支持未来重新接手开发，能够快速理解系统、完成本地部署、定位故障并规划下一阶段工作。

## 交付形式

- 在项目根目录新增 `PROJECT_HANDOFF.md`，作为阶段性交接主文档。
- `README.md` 继续承担 GitHub 对外项目主页职责，不复制过多内部复盘细节。
- 交接文档采用“产品复盘与简历证据 + 技术交接”双层结构。

## 第一层：产品复盘与简历证据

应包含：

- 项目摘要、目标用户、核心 JTBD 与产品初衷；
- 从底部实时字幕到可移动视频理解伴侣的迭代时间线；
- 关键决策、替代方案、放弃原因及质量/延迟/成本取舍；
- AI 产品经理能力与实际证据的映射；
- 已验证、仅观察、尚未验证三档证据表；
- 可安全写入简历的表述、可量化事实和禁止夸大的指标；
- 失败、根因、产品改变、复测结果及重新开始时的优先验证项。

## 第二层：技术交接

应包含：

- 系统架构、数据流与三类 Agent 的职责边界；
- 关键目录、文件、接口、WebSocket 事件和修改入口；
- Windows 本地部署、构建、启动、健康检查与测试方法；
- 环境变量名称、密钥管理和轮换原则，不记录任何真实密钥；
- 数据存储现状：当前无持久化数据库，使用进程内 SessionStore；
- 常见故障的症状、根因、检查顺序与处理方法；
- 已知风险、技术债务、隐私边界和下一阶段路线图；
- GitHub 分支、提交、PR 与阶段性交付清单。

## 证据规则

- 只记录能从代码、测试结果、构建结果或真实排障过程验证的事实。
- 用户量、留存率、翻译准确率、延迟改善比例等未采集数据不得虚构。
- 将“系统已实现”“人工实测观察”“未来建议指标”明确分开。
- 简历表述优先采用“决策—证据—结果”，避免功能流水账和模型名词堆砌。

## 安全规则

- 不在 README、交接文档、提交记录或 PR 中写入真实 API Key。
- 只引用 `backend/.env.example` 中的变量名和公开默认值。
- 明确说明音频会经过本地后端发送至阿里云百炼，当前会话数据仅保存在内存中。

## 完成标准

- 文档不存在 `TODO`、`TBD`、真实密钥或无法证实的效果数字。
- README 与交接文档对架构、模型、部署方式和数据存储的描述一致。
- 后端 12 项单元测试通过，前端 TypeScript 检查与 Vite 构建通过。
- GitHub Description 已更新，PR 合并到 `main`，远程主分支包含完整源码和文档。
